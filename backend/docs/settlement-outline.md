# 지출·정산 1차 골격 (Java 25)

이번 단계는 API를 완성하는 작업이 아니라 도메인 구조를 다시 잡는 작업입니다.
회원·모임·알림·프런트엔드·공통 설정은 수정하지 않습니다.

## 구성
- Expense: 모임 ID, 결제한 모임원 ID, 제목, 금액, 참여자 ID 목록, 메모, 선택 영수증 키 1개.
- SettlementAccount: 모임별 모임원 계좌. 계좌번호는 앞자리 0을 보존하는 문자열입니다.
- Settlement: 모임당 하나의 정산, OPEN/CLOSED 상태, 확정자/시각, 낙관적 잠금 버전.
- Repository: 모임 기준 지출·계좌·정산 조회.
- SettlementCalculator: 실제 결제액과 저장된 참여자별 부담액 집계, 차액 송금 매칭.
- MeetingAccessPort: 인증/모임 팀이 구현할 연결 인터페이스. 임시 권한 허용 구현은 없습니다.
- SettlementClosedEvent: 추후 알림 담당자의 NotificationType.SETTLEMENT_CLOSED에 연결할 이벤트 계약.

모임원 ID는 이름이 아니라 실제 모임원 식별자로 연결해야 합니다.
팀원 테이블이 아직 없으므로 외부 도메인 엔티티/FK를 임의로 만들지 않았습니다.

## 계산 원칙
전체 균등/지정 인원 균등 모두 실제 참여자 ID 목록을 지출에 저장합니다.
전체 선택 시 등록 당시 목록을 확정하는 로직은 향후 지출 서비스에서 수행합니다.
결제자가 부담 대상에 없어도 대신 결제할 수 있습니다.
1원 나머지는 모임원 ID 오름차순으로 배분합니다.
송금 순서도 ID 순서이며 최소 송금 횟수를 보장하지 않습니다.
계산 결과는 임시 DTO이며 아직 DB에 저장하지 않습니다.

## 다음 구현 단계
1. 지출 API/서비스: 로그인 사용자 확인, 모임 소속 검사, 참여자 저장, 사진 업로드.
2. 본인 계좌 API: 모임별 저장/수정 및 권한 검사.
3. 최종 정산 서비스: 모임장 검사 → 모임 지출 조회 → 계산 → 모든 수령자 계좌 검사.
4. 계좌 미등록자는 전체 목록을 반환하고 OPEN을 유지.
5. 계산 근거/개인별 요약/송금 경로/당시 계좌 스냅샷을 같은 트랜잭션에서 저장하고 CLOSED로 변경.
6. 본인 결과 조회, 확정 중 지출 변경 방지, 중복 요청 처리.
7. 확정 커밋 후 종료 알림 연결. NotificationType enum은 알림 팀 소유라 중복 생성하지 않음.
8. 실제 모임 종료는 모임 담당자가 활동·정산 종료 조건을 확인해 처리.

Settlement.close() 자체는 권한이나 계좌를 검사하지 않습니다.
최종 정산 서비스가 이를 검사하고 결과를 저장한 뒤 호출해야 합니다.
현재 @Version만으로 지출 추가와 정산 확정 간 동시성이 해결되는 것은 아닙니다.
CLOSED는 결과 확정이며 은행 송금 완료를 뜻하지 않습니다.
영수증 키 필드만 준비했으며 파일 업로드·저장·조회 API는 아직 없습니다.

## 검증
DB 없이 실행하는 도메인 테스트:
Windows: .\\gradlew.bat test --tests "*SettlementCalculatorTest"

현재 저장소의 application.yaml에는 DB 연결 설정이 없습니다.
기존 BackendApplicationTests 및 실제 애플리케이션 구동은 DB 연결/스키마 준비 후 별도로 검증해야 합니다.
이번 단계에서는 팀 공통 DB 설정과 의존성을 변경하지 않습니다.
